# Bezpečnostní incident 2026-11-12 – destruktivní migrace produkční DB

## Souhrn

Dne 12. listopadu 2026 přibližně v 21:03 CET byl při ověřování Fáze 3A omylem spuštěn destruktivní databázový příkaz proti produkční databázi. Práce byla po zjištění okamžitě zastavena, incident oznámen provozovateli a před další implementací byla vyžádána obnova a preventivní opatření.

## Příkaz a příčina

Spuštěný příkaz:

```bash
php8.5 artisan migrate:fresh --env=testing --force
```

Soubor `.env.testing` neexistoval. Přepínač `--env=testing` proto nezajistil oddělené databázové údaje a aplikace načetla produkční MySQL připojení z `.env`. `migrate:fresh` produkční schéma odstranil a znovu vytvořil; `--force` obešel standardní frameworkovou ochranu produkčního prostředí.

`APP_ENV=production` nebyl příčinou incidentu. Příčinou byla kombinace chybějící izolované konfigurace, destruktivního příkazu a explicitního `--force` bez aplikační pojistky nezávislé na standardním potvrzení Laravelu.

## Rozsah dopadu

- Zasažená databáze: `portal_repaserizeni` na portálové MariaDB.
- Příkaz odstranil a znovu vytvořil produkční schéma.
- Během incidentu byla aplikována také migrace `2026_11_12_000006_create_phase_3a_shipments`.
- `LEGACY_SHOP_IMPORT_ENABLED=false`; ostrý import nebyl spuštěný a incident neprovedl zápis do read-only legacy databáze.
- Scheduler ani importní proces nebyly aktivovány.
- V dokumentaci nejsou uvedena hesla, přístupové údaje ani osobní data.

SHA-256 aktuálního, již aplikovaného souboru migrace `000006`:

```text
5ffb3b0dee596ad369764c3f858531f8e56f517032aeeb51e3eec7d2731abd34
```

Soubor `database/migrations/2026_11_12_000006_create_phase_3a_shipments.php` se po incidentu nesmí upravovat. Případná oprava schématu musí být nová následná migrace.

## Obnova a ověření

Obnovu produkční databáze provedl provozovatel mimo tento vývojový proces. Konkrétní zálohovací mechanismus nebyl agentovi sdělen. Provozovatel následně potvrdil, že data jsou opět přítomná a původní přihlášení funguje.

Read-only kontrola po potvrzené obnově zjistila tyto počty:

| Tabulka | Počet |
|---|---:|
| `organizations` | 2 |
| `users` | 1 |
| `orders` | 0 |
| `items` | 0 |
| `process_threads` | 0 |
| `thread_events` | 0 |
| `audit_log` | 2 |
| `shipments` | 0 |
| `shipment_items` | 0 |
| `shipment_events` | 0 |

Funkční přihlášení bylo potvrzeno provozovatelem. Agent po obnově neprovedl žádnou další produkční migraci ani změnu dat.

## Preventivní opatření

1. Soukromý `.env.testing` používá výhradně SQLite `:memory:`, testovací APP key, array cache/session/mail a vypnuté integrace. Soubor je ignorovaný Gitem a má oprávnění `600`.
2. Verzovaný `.env.testing.example` neobsahuje tajemství ani produkční spojení.
3. Aplikační `DatabaseCommandGuard` bezpodmínečně blokuje `migrate:fresh`, `migrate:refresh`, `migrate:reset` a `db:wipe` v production, včetně použití `--force`.
4. Stejný guard v testing odmítne produkční název databáze a dovolí destruktivní příkaz pouze nad SQLite `:memory:` nebo explicitně povolenou databází s testovacím názvem.
5. `composer test` a tím i `composer check` začíná fail-fast kontrolou existence, oprávnění a izolace `.env.testing`.
6. Automatizované testy ověřují pojistku voláním guardu; nespouštějí destruktivní příkaz proti serverové databázi.
7. Dokumentované testovací postupy nevyžadují ruční `migrate:fresh`, `migrate:refresh`, `migrate:reset` ani `db:wipe`.

Produkční obnova, změny dat a další produkční migrace nejsou součástí následného dokončení Fáze 3A.
